# Scout-агент — дизайн (v1)

## Контекст и цель

Первый агент в цепочке "берём заказы на биржах и делаем их" (см. [[jarvis-agent-setup]], [[landing-service-jarvis-verification]]). Александр уже умеет закрывать лендинги/визитки и Telegram-ботов через связку Jarvis + Claude Code, но заказы неоткуда брать автоматически. Scout закрывает именно поиск и первичный отбор заказов — фильтрует источники по 5 направлениям (лендинги, визитки, Telegram-боты, ИИ-ассистенты для бизнеса, парсинг/автоматизация, деплой серверов под ключ) и уведомляет в Telegram. Оценку "сделаю/не сделаю" и цену Александр в v1 делает сам — Scout не предлагает feasibility-оценку через LLM (риск неточных оценок, лишняя сложность на старте).

## Ограничение: самозанятость

На момент дизайна (2026-09-11) у Александра нет статуса самозанятого — оформит примерно через неделю. Это временное, а не структурное ограничение, но оно определило выбор площадок для v1.

## Выбор площадок

- **Хабр Фриланс — исключён.** Площадка закрылась 28.02.2025, заказов там больше нет (только новостная лента на Habr).
- **FL.ru — основной источник.** Самозанятость не обязательна: полный доступ к откликам даёт либо самозанятость, либо привязка банковских реквизитов. У FL.ru есть официальная RSS-лента заказов с фильтрацией по категории/подкатегории (`fl.ru/rss/...?category=X&subcategory=Y` — точный формат нужно проверить на месте при реализации, источник схемы 2019 года). RSS — предназначенный для мониторинга канал, не HTML-скрейпинг.
- **Avito Услуги — вне автоматизации v1.** Раздел "Заказы" с заявками клиентов существует, но у Avito нет публичного RSS/API, и жёсткая защита от скрейпинга (капчи, IP-блокировки). Остаётся ручным каналом: Александр размещает своё объявление и сам проверяет отклики.
- **Kwork — отложен.** Площадка двигается к работе только с самозанятыми/ИП: без этого статуса комиссия 7% вместо 1% и нет доступа к заказам от юрлиц. Имеет смысл подключать после оформления самозанятости (~через неделю от даты дизайна), не в v1.

## Второй источник — Telegram-чаты

Помимо FL.ru, заказы по направлениям Александра циркулируют в Telegram-чатах фрилансеров. Александр пока не состоит в конкретных таких чатах — их подбор и вступление это отдельная ручная задача вне сборки Scout (можно помочь подобрать отдельным шагом позже).

Технически бот (Bot API) не может слушать произвольные групповые чаты без прав администратора, которых там не будет. Поэтому доступ — через MTProto-сессию **личного аккаунта** Александра (например, через GramJS), запущенную на VPS. Александр осознанно принял этот риск (сессия аккаунта — чувствительные данные, хранится только на его VPS).

## Архитектура

Три независимых юнита на VPS `rpluripwwk` (см. [[jarvis-bot-deployment]]), код в `~/projects/scout` — по аналогии с `~/projects/vizitka-landing-pages`, не в защищённой `~/.agent/` (там только рантайм-зона agent-bot).

### 1. `scout-fl` (периодический)
- systemd timer, запуск каждые 10–15 минут.
- Тянет RSS FL.ru по сконфигурированным категориям.
- Парсит каждый пункт (название, ссылка, бюджет если указан, ID).
- Фильтрует через общий модуль ключевых слов (см. ниже).
- Сверяет ID с локальным файлом "уже отправлено" (JSON) — дедупликация.
- Новые совпадения → в общий Telegram-нотификатор; ID дописывается в файл. Записи старше ~14 дней подчищаются.

### 2. `scout-tg` (постоянный)
- systemd service с `Restart=always` (как agent-bot) — держит открытое MTProto-соединение.
- Слушает новые сообщения в чатах из конфига (список chat ID/username, изначально пустой — заполняется Александром по мере вступления в чаты).
- Каждое новое сообщение проходит через тот же общий модуль ключевых слов.
- Дедупликация по ID сообщения (на случай переподключений).
- Совпадения → тот же общий Telegram-нотификатор.

### 3. Общие модули (shared, без дублирования логики)
- **Фильтр по ключевым словам** — принимает текст, возвращает совпавшее направление или `null`. Один конфиг ключевых слов на все 5 направлений, используется и `scout-fl`, и `scout-tg`.
- **Telegram-нотификатор** — прямой вызов Bot API `sendMessage` в личный чат Александра (можно тем же токеном, что у agent-bot). Не идёт через очередь Claude в agent-bot — не должен зависеть от его состояния и не должен его нагружать.

### Формат уведомления (v1 — только факты)
- Источник (FL.ru / название чата).
- Название/текст заказа.
- Направление (какое из 5 совпало).
- Бюджет, если указан.
- Ссылка на заказ (для FL.ru) или на сообщение (для Telegram, если применимо).

## Обработка ошибок

- RSS недоступен / сайт лежит → лог, пропуск цикла. Предупреждение в Telegram только после N подряд неудачных циклов (например, 6 = час простоя), не на каждый цикл — не спамить.
- RSS не распарсился (формат изменился) → лог ошибки, пропуск, то же правило "не чаще раза в час".
- MTProto-соединение оборвалось → systemd `Restart=always` поднимает `scout-tg` заново; переподключение не должно приводить к повторной отправке уже виденных сообщений (дедупликация по ID).

## Секреты и безопасность

Ничего из перечисленного ниже не должно попасть в git, в логи или куда-либо за пределы VPS.

- **Секреты Scout:** `BOT_TOKEN` (для нотификатора), `api_id`/`api_hash` для MTProto (с my.telegram.org), сессия MTProto-аккаунта (`scout-tg`) — это фактически ключ доступа к личному Telegram-аккаунту Александра, самый чувствительный файл во всей системе.
- **Хранение:** отдельный `.env` в `~/projects/scout` (не общий с agent-bot — так баг в одном компоненте не может утащить за собой секреты другого, тот же принцип изоляции, что и в остальном дизайне). Файл сессии MTProto — отдельно, права `chmod 600`, владелец — тот же пользователь, что запускает `scout-tg` (без доступа других пользователей системы).
- **git:** `.env`, `*.session` и любые файлы с секретами — в `.gitignore` репозитория/директории Scout с первого коммита, до того как там появится хоть один секрет.
- **Логи:** нигде не логируется значение токена, `api_hash` или содержимое сессии. Ошибки подключения логируются без дампа этих значений.
- **Урок из инцидента с `.env` agent-bot** (см. [[jarvis-bot-deployment]]): любой код, который пишет файлы с секретами (`.env`, файл сессии), обязан делать атомарную запись с бэкапом перед перезаписью — тот баг `safeEnvRemove` затирал `.env` в 0 байт именно из-за отсутствия такой защиты. Та же дисциплина применяется к Scout с самого начала, а не добавляется постфактум.
- **Бэкапы:** если сессия или `.env` когда-либо копируются (бэкап VPS и т.п.) — только в приватное хранилище, никогда не в публичный или общий репозиторий.

## Тестирование

- Юнит-тест парсинга и фильтрации на сохранённом примере RSS-ответа (без реального обращения к FL.ru).
- Юнит-тест общего модуля ключевых слов на наборе примеров текста → направление.
- Ручная проверка: разовый запуск `scout-fl` на реальном фиде; проверка, что systemd timer триггерится по расписанию (`systemctl status`, `journalctl`).
- Для `scout-tg`: ручная проверка на тестовом чате (можно временно добавить сам аккаунт в приватный чат с самим собой) до подключения к реальным чатам с заказами.

## Вне рамок v1 (сознательно отложено)

- AI-оценка сложности/цены заказа перед уведомлением — только факты в v1.
- Kwork — после оформления самозанятости.
- Автоматизация Avito Услуги — риск по ToS, остаётся ручным каналом.
- Подбор и вступление в конкретные Telegram-чаты с заказами — отдельная ручная задача, не часть сборки Scout.
- Исполнители по направлениям (веб/боты/ИИ, инфра) — Scout закрывает только источник заказов, не их выполнение.
