# scout-tg — дизайн

## Контекст и цель

Второй источник заказов для Scout-агента (см. [[jarvis-agent-setup]]), дополняющий уже развёрнутый и работающий `scout-fl` (мониторинг RSS FL.ru, репозиторий `funnyalexsteam-maker/scout-agent`, VPS `rpluripwwk`). Концепция описана в исходной спеке `2026-09-11-scout-agent-design.md` ("Второй источник — Telegram-чаты") и была сознательно отложена до того, как scout-fl подтвердит себя в бою — это условие выполнено.

scout-tg слушает Telegram-чаты, где Александр уже состоит, и находит в них заказы по тем же 5 направлениям (лендинги/визитки, Telegram-боты, ИИ-ассистенты, парсинг/автоматизация, деплой серверов), переиспользуя уже написанные и проверенные модули `keywordMatcher.js` и `notifier.js`.

## Структура: тот же репозиторий

scout-tg добавляется в `funnyalexsteam-maker/scout-agent` — не отдельным репозиторием. Один `npm install`, один набор тестов, один уже настроенный deploy-key на VPS. `keywordMatcher.js` и `notifier.js` используются без изменений — они и создавались с расчётом на это переиспользование.

## Доступ к чатам: MTProto под личным аккаунтом

Бот (Bot API) не может слушать произвольные групповые чаты без прав администратора. Единственный рабочий способ — MTProto-сессия **личного аккаунта** Александра через **GramJS** (`telegram` на npm — зрелая, активно поддерживаемая MTProto-библиотека для Node.js). Александр осознанно принял этот риск ранее в проекте: сессия аккаунта хранится только на его VPS, доступ к которому уже ограничен.

## Секреты и хранение

- `TG_API_ID` / `TG_API_HASH` — с my.telegram.org, добавляются в тот же `.env`, что и `BOT_TOKEN`/`NOTIFY_CHAT_ID`.
- Файл сессии MTProto (`*.session`) — уже в `.gitignore` репозитория с первого коммита scout-fl, дополнительных изменений не требуется.
- Та же дисциплина атомарной записи (temp-файл + rename) применяется к любому файлу состояния, который пишет scout-tg на диск.

## Список чатов и как его пополнять

- `data/tg-chats.json` — не в git (папка `data/` уже гитигнорена), по умолчанию `[]`.
- Формат записи — предпочтительно Telegram-юзернейм (`"@freelance_orders_chat"`); для приватных групп без юзернейма — числовой chat ID.
- **Как добавлять:** Александр вступает в чат → просит Jarvis (или Claude Code через SSH) дописать чат в `data/tg-chats.json` и перезапустить сервис (`systemctl --user restart scout-tg.service`), чтобы список подхватился. Список чатов сейчас пуст — сервис будет разворачиваться без единого чата и не найдёт ничего, пока чаты не добавят.
- Отдельный вспомогательный скрипт `src/listMyChats.js` — разово выводит все чаты, где состоит аккаунт, с их ID и названиями. Нужен для приватных групп без юзернейма, чтобы не гадать с ID вручную.

## Архитектура и поток данных

1. `src/tgListener.js` — постоянный процесс: поднимает MTProto-сессию из сохранённого файла, подписывается на новые сообщения (`NewMessage`) только в чатах из `tgChats.js`/`data/tg-chats.json`.
2. Каждое новое сообщение → `matchDirection(text)` из `keywordMatcher.js`.
3. Совпадение → дедупликация по паре `(chatId, messageId)` — переиспользуется тот же принцип, что и в `dedupStore.js` (атомарная JSON-запись, метод `has`/`add`), файл состояния `data/seen-tg.json` (по аналогии с `data/seen-fl.json`).
4. Новое совпадение → `sendTelegramMessage` из `notifier.js`, в **того же выделенного бота** ("Scout Заказы"), что и уведомления от scout-fl — все заказы стекаются в одно место, независимо от источника.
5. Формат уведомления — те же факты: источник (название чата), текст сообщения (обрезанный по той же логике, что уже есть для описаний FL.ru), направление, ссылка на сообщение (если применимо).

## Деплой: не таймер, а постоянный сервис

В отличие от `scout-fl.timer` (периодический опрос), scout-tg держит открытое соединение — это `scout-tg.service` (systemd `--user`, `Restart=always`, как agent-bot). `linger` для пользователя `agent` уже включён (сделано при деплое scout-fl) — переживёт отключение SSH.

**Первый запуск требует интерактивного шага**, который нельзя автоматизировать полностью:
1. Александр получает `TG_API_ID`/`TG_API_HASH` на my.telegram.org (это может сделать только он — требует входа под его номером).
2. Логин MTProto-сессии — нужен номер телефона и код из Telegram (+ пароль 2FA, если включён) в реальном времени. Выполняется через SSH+tmux (тот же приём, которым ранее настраивалась авторизация Jarvis на сервере): Claude Code вводит номер, Александр присылает код из Telegram, Claude Code подставляет его в диалог.
3. После успешного логина сессия сохраняется в файл — повторный интерактивный вход не требуется, пока сессия валидна.

## Обработка ошибок

- Обрыв MTProto-соединения → GramJS переподключается сам; `Restart=always` — подстраховка на случай падения процесса целиком.
- Ошибка при отправке одного уведомления в Telegram → лог + пропуск этого сообщения, не должна ронять весь процесс (тот же принцип изоляции ошибок, что был добавлен в scout-fl после финального ревью).
- Список чатов пуст → сервис стартует нормально, просто ничего не слушает; не считается ошибкой.

## Тестирование

- Юнит-тесты дедупликации по `(chatId, messageId)` — по аналогии с `dedupStore.test.js`.
- `matchDirection`/`sendTelegramMessage` уже протестированы в scout-fl, повторно не тестируются.
- Собственно приём сообщений через реальный MTProto — не юнит-тестируется; проверяется вручную после деплоя (сообщение в тестовый чат → появляется уведомление).

## Вне рамок

- Подбор и вступление в конкретные чаты — ручная задача Александра, не часть этой сборки.
- Никакой AI-оценки сложности/цены — только факты, как и в scout-fl.
- Публичные каналы, где нужно быть админом для чтения через Bot API, — не рассматриваются; вся история строится на MTProto-доступе как участника.
